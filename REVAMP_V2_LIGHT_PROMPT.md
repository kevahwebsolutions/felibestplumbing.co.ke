## 2. Task B: orders go to WhatsApp automatically

Business WhatsApp number comes from the admin settings (default +254 798 174 201). Currency KES. Build:

1. Order flow: checkout still saves the order in the database first (public reference) and shows `/order/[ref]`. Immediately after a successful save, the browser is redirected automatically to `https://wa.me/<number>?text=<encoded order message>` (same-tab redirect on mobile, new-tab attempt with a fallback on desktop to avoid popup blockers). The `/order/[ref]` page also shows a large green "Send order on WhatsApp" button and a note that the order is already saved even if the customer does not send the message. A product page also gets an "Order this on WhatsApp" quick button that sends that single product the same way (also saved as an order).
2. Message builder (pure, unit-tested, in one shared module): order reference, customer name, phone, delivery area, address, notes, payment choice, then for EACH item: name, quantity, unit price, line total, and the absolute product URL (`NEXT_PUBLIC_SITE_URL` + `/shop/<slug>` or the real product route). Then delivery fee, total, and a link to `/order/[ref]`. Plain text with simple line breaks, no emojis. Keep the encoded URL under about 1900 characters: if a long cart would exceed it, list the first items in full, summarise the rest ("and N more items, see order link"), and always keep the order link. Never include secrets. Sanitise customer input (strip control characters, cap lengths).
3. Product image in WhatsApp: a wa.me link cannot attach images, so the image arrives as the link preview when the message contains a product URL. Make that work properly: each product page needs correct `generateMetadata` with `og:title`, `og:description`, `og:url`, `og:type`, and `og:image` pointing to a JPEG (WhatsApp does not reliably render WebP previews). Add a route handler `/og/product/[slug]` that returns a 1200x630 JPEG (sharp: product primary image on a white background with the Felibest logo and the KES price), cached with sensible headers. Also set the order page's metadata with `robots: noindex`. Add a short note in the README that previews only render on the deployed public domain, not on localhost.
4. Optional fully automatic send (server to the owner's WhatsApp, no customer action): implement a `OrderNotifier` interface with two implementations. (a) `WhatsAppLinkNotifier` is the default and is just the behaviour above. (b) `WhatsAppCloudNotifier` uses the Meta WhatsApp Cloud API (Graph API `POST /{phone-number-id}/messages`), enabled only when `WHATSAPP_CLOUD_TOKEN`, `WHATSAPP_PHONE_NUMBER_ID` and `WHATSAPP_OWNER_NUMBER` are set. It sends the owner an image message (first product's JPEG from the `/og` route or the product image URL as the header, order summary as the caption) and falls back to a template message when outside the 24-hour window, with the template name in `WHATSAPP_TEMPLATE_NAME`. It runs after the order is saved, never blocks or fails checkout, retries once, logs only non-sensitive status, and records `whatsappNotifiedAt` and `whatsappNotifyError` on the order (add a Drizzle migration). Show a "WhatsApp: sent / not sent" badge in the admin orders list and detail. Add all variables to `.env.example` with comments and a README section "Enable automatic WhatsApp (Cloud API)" with the steps (Meta business account, phone number ID, permanent token, template approval). Never log or return tokens. Unit-test both notifiers with a mocked `fetch`.
5. Admin: orders list shows new orders first with a prominent "New" state and an "Open in WhatsApp" button that opens a chat with the customer (`wa.me/<customer phone>`) with a prefilled confirmation message. Order detail shows the same message the customer sent.
6. Analytics: keep `order_placed` and `whatsapp_click` events; add `whatsapp_order_redirect`.
